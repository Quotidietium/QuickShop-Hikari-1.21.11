## 二、修复清单（13 项，全部附验证）

### 批次 A：经济数值与计量（数据正确性）

1. **`CalculateUtil` DECIMAL32 精度缺陷**（`quickshop-common/.../CalculateUtil.java`）：add/subtract/multiply 使用 `MathContext.DECIMAL32`（7 位有效数字）——`1234567.89 × 64 = 79012344.96` 被舍入为 `79012340`，±0.5 分位的系统性误差方向由舍入方向决定（买家多付或店主少收）；默认价格上限 1e29 下误差可达天文级。加/减/乘改为精确算术（参与运算的都是 double 最短十进制表示，尺度有界、必然终止），除法保留 MathContext（DECIMAL64，可非终止）。测试 `CalculateUtilExactMathTest` 钉住精确性与守恒式。
2. **税率换算二进制噪声**（`SimpleShopManager.java` 四处）：`new BigDecimal(effectiveTax.xxxRate())` 保留 0.05 的完整二进制展开（0.05000000000000000277…），此前靠 DECIMAL32 舍入掩盖；改 `BigDecimal.valueOf(...)`（最短十进制表示）后与精确算术配套，税额拆分到分位精确且 `afterTax + tax == amount` 恒成立。
3. **免费商店 "all" 零价格除零**（`SimpleShopManager.sellingShopAllCalc` 与 `ShopUtil.sellingShopAllCalc` 两处副本）：`balance / price` 在 price=0 且 balance=0 时为 0/0=NaN → `(int)NaN = 0` → 免费店空余额玩家输入 all 被误报「买不起」且无法交易（balance>0 时走 Infinity→MAX_VALUE 恰好正常，掩盖了缺陷）。全部五个同族计算（buyingShopAllCalc ×2、getPlayerCanSell、getMaxAffordable）均已有零价守卫，唯独两处 sellingShopAllCalc 缺失。修复：`price > 0 ? floor(balance/price) : MAX_VALUE`。测试 `FreeShopAllCalcTest` 反射钉住三场景（零余额免费店可交易、正价零余额仍拒绝、正余额免费店正常）。
4. **失败预览 allowedAmount 双重除法**（`SimpleTradeService.java` 买/卖两处）：`Util.countItems` 返回的已是「交易份数」，`allowedTrades = stock / stackSize` 再除一次 unitSize——堆叠店（unitSize=16）库存 35 个（2 份可交易）时 API 报告 allowedAmount=0。第三方消费 TradePreview/TradeResult.allowedAmount 时被低估 unitSize 倍。测试 `TradePreviewAllowedAmountTest` 三用例（买侧/卖侧/普通店不变）。
5. **`/qs refill all` 单位缩水**（`SubCommand_Refill.java`）：`getRemainingSpace()`（份数）直接喂给 `shop.add(item, amount)`（物品数）——堆叠店 refill all 只填满 1/unitSize 的空间。修复：`space * max(1, unitSize)`（无限店返回 -1 的既有 no-op 语义保持）。
6. **回执/店主通知单位不一致**（`SimpleShopManager.sendSellSuccess/notifySold`）：买入方向显示物品数（`amount × unitSize`）、卖出方向显示交易份数（`amount`）——堆叠店卖 2 份（32 个物品）回执写「卖出了 2 个」。统一为物品数（与 sendPurchaseSuccess/notifyBought 对齐，普通店 unitSize=1 输出逐位不变）。

### 批次 B：聊天输入链（用户交互正确性）

7. **QSHandleChatEvent null 消息 NPE**（`SimpleShopManager.handleChat`）：事件 setMessage 无校验，第三方插件置 null 后 `actionTrade` 的 `message.equalsIgnoreCase(tradeAllKeyword)` 在调度任务内 NPE 且会话已被消耗——玩家零反馈静默失败。空/null 消息现在直接返回且**不消耗会话**（输错可重试）。
8. **pending 会话覆盖竞态**（`handleChat`）：异步捕获 pending A → 调度 1 tick → 窗口内玩家点击商店 B（put 覆盖同 UUID）→ 任务取出 B 并用 A 的消息对 B 执行交易。宏/改客户端可稳定构造。修复：remove 后比对引用标识，不一致则回填 B、丢弃过期应答。
9. **GUI 聊天输入双消费**（`ChatListener`）：玩家同时存在交易待处理与 GuiChatInputManager 待输入时，同一条消息被两处消费（GUI 输入生效的同时按旧提示买了商店的东西）。修复：ChatListener 检测到 GUI 待输入即让位（该管理器自行取消并消费事件）。
10. **ChatListener 调试文案与代码语义相反**：代码语义（config 注释为准）是「ignore-cancel-chat-event=true → 跳过已取消事件」，调试文本却写「开启可强制处理」。修正文案。（行为本身不动——默认 false 处理已取消事件是 LiteBans 静默玩家仍可交易的支持路径。）

### 批次 C：管理命令数据安全

11. **`/qs database purgelogs` 符号反转**（`SubCommand_Database.java`）：`calendar.add(DATE, days)` 把正数天数加到当前时间——按提示输入 `30`（想删 30 天前的日志）实际删除**全部**日志（只有输入 -30 才符合直觉）。修复：`-days` 且负数输入直接拒绝。
12. **`/qs database save` 主线程阻塞**（同文件）：`CompletableFuture.allOf(...).join()` 最长 15s + 超时回退逐店 `updateSync()`，商店多/DB 慢时全服卡顿。整段移入异步线程（`Shop.update()` 文档明示可异步调用），完成时发送新语言键 `database.save-complete`。
13. **`/qs setowner` 幽灵属主**（`SubCommand_SetOwner.java`）：`FastPlayerFinder.name2Uuid` 永不返回 null（静默回退到确定性离线哈希 UUID），拼错的名字把商店转给永无人可认领的幽灵 owner，null 检查是死代码。修复：`Bukkit.getPlayerExact` 或 `getOfflinePlayerIfCached`（Paper 原生，查 usercache）双查不认识即拒绝。
14. **破坏性命令确认门**（`SubCommand_Clean/RemoveWorld/RemoveAll`）：一次误触即全服/全玩家/整世界删店且每店触发经济退款，此前无任何确认（CleanGhost/Recovery/Database trim 均已有确认先例）。三个命令统一加 `confirm` 参数门 + 新警告语言键（`command.clean-warning`/`command.removeall-warning`/`removeworld-warning`，en+zh_cn）。顺带修正 Clean 计数漏加 IllegalStateException 分支（改用队列实际大小）。
15. **Recovery 导入失败后空内存运行**（`SubCommand_Recovery.java`）：先 unload+clear 内存再异步导入，导入抛异常时只报错——插件带零商店继续运行、交易功能静默失效。修复：失败分支先失效 DB 写路径缓存（部分导入可能已换表）再从数据库重载商店恢复服务。
16. **TransferAll 管理员双参路径缺自转检查**（`SubCommand_TransferAll.java`）：1 参路径有 from==to 拦截、2 参强制路径没有。补齐。

### 批次 D：杂项交互缺陷

17. **createShop 价格上限分支显示错值**（`SimpleShopManager.createShop`）：`REACHED_PRICE_MAX_LIMIT` 的非格式化路径误用 `getMin()`（复制粘贴错误，ShopUtil.setPrice 同分支用 getMax 正确）。
18. **tab-complete 大小写不一致**（`SimpleCommandManager.onTabComplete`）：执行路径 `equalsIgnoreCase` 不区分大小写、补全路径 `prefix.toLowerCase().startsWith(cmdArg[0])` 区分——`/qs HE<tab>` 无补全但 `/qs help` 可执行。
19. **`SimpleInfo.hasChanged` null 埋雷**：5 参构造器不设 shopData（null），`setAction` 可后续翻转为 trading 动作，届时 NPE。null 时安全返回「已变更」（fail-safe）。
20. **`/qs reset config` 静默失败**（`SubCommand_Reset.java`）：`config.delete()` 返回值被忽略，文件锁等导致删除失败时仍报 complete（saveDefaultConfig 不会覆盖已存在文件，实际什么都没重置）。失败现在如实报错。

## 三、完好不变式抽样（验证未破坏）

- **经济守恒**：`QSEconomyTransaction` 提交路径 withdraw(fromAmount) = deposit(afterTax×份额) + deposit(owner 余款) + deposit(totalTax)，各字段以减法定义（toTax=amount−afterTax、fromTax=fromAmount−amount），精确算术下恒守恒；benefit 非法份额（≤0/null）拒付且不虚增 owner 余款（R36 修复仍在，`QSEconomyTransactionTest` 8 用例全绿——改精确算术后旧断言 compareTo 全部通过，证明小额度行为逐位不变）。
- **交易预检-执行同源**：preview 与 commit 共享同一次 symbolLink 解析（R48/R51 结论仍成立）；`validateTradeAmount` 的 unitSize=0/溢出守卫（9c88938d5 修复）仍在且前置。
- **价格限制器**：默认 undefinedMin=0.0 挡负价、wholeNumberOnly/NOT_VALID 路径完好；规则加载失败跳过不致崩。
- **命令权限**：REQUIRE 全满足/SELECTIVE 任一满足的双轨语义、disabledSupplier 门（size/purge/tag 族）、执行与补全双查——均验证无绕过。
- **hasListeners 门控**（R46-R52 的构造门）在本轮触碰的路径上语义未变：门内代码逐位保持。

## 四、已接受残留（带理由）

| # | 残留 | 理由 |
|---|---|---|
| 1 | deleteShop「退款→卸载→注销」中 DB 删除失败无回滚，重启后商店复活可致二次退款 | 修复需跨经济/DB 的分布式事务；DB 删除失败本身极罕见（EasySQL 重试），复活商店可再删；与 R36 结论一致留档 |
| 2 | taskCache 跨命令（transferownership/transferall）任务混淆与静默覆盖 | 接收方 accept 始终是获益方向（收下商店）、两个 ask 消息均指明正确命令；加任务类型字段需新语言键且收益有限 |
| 3 | Recovery 的 clear() 在主线程最长阻塞 30s | 隐藏命令+控制台专用+极低频；卸载循环需 region 线程协调，重构风险大于收益 |
| 4 | `/qs database purgeplayerscache` 无确认 | 纯缓存表（玩家名查找缓存），自动重建，无数据损失 |
| 5 | RemoveWorld/RemoveAll 报数为「已调度删除数」，ShopDeleteEvent 被第三方取消时虚高 | deleteShop 返回 void，精确计数需改 ShopManager API 返回类型（破坏第三方二进制兼容）；取消本身罕见且有日志 |
| 6 | Folia 下 handleChat 在商店 region 线程读玩家位置（SimpleShopManager.java:1055 附近） | Paper（主目标）上 regionThread=主线程安全；Folia 为次级目标，代码库同类读取多处存在，需系统性方案 |
| 7 | 玩家名解析大小写不一致 + `unknown-player` 文案在「离线」场景误导（TransferAll 双参路径要求双方在线） | 在线检查兜底了所有有害方向；文案打磨需新语言键 |
| 8 | `CountableInventoryWrapper.countItem/countSpace` 未定义单位契约（仓库内无实现） | 第三方接口扩展点；文档化于 javadoc 的收益与本轮范围外 |
| 9 | ChatListener 监听已废弃的 AsyncPlayerChatEvent（Paper 双事件不联动）、LiteBans 前缀硬编码 | 换 AsyncChatEvent 是行为变更（取消状态语义不同），前缀剥离无害 |
| 10 | 死亡/换世界不清理 pending 会话（退出/移动/传送/方块破坏均清理） | handleChat 执行前的世界+距离复检兜底，无法绕过形成实际损害 |
| 11 | TransferOwnership 的 commit 未包 mainThreadRun（Folia 区域一致性） | Paper 等价；与 Purger 的 runAtLocation 模式统一属 Folia 专项 |
